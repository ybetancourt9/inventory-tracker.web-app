# Milestone Two Narrative: Software Design and Engineering

Yaumel Betancourt

CS 499 Computer Science Capstone

Southern New Hampshire University

07/26/2026

The artifact is an inventory tracker application that I originally built in CS 360 Mobile Architecture and Programming. It was an Android application written in Java that stored its data in a local SQLite database on the device. It displayed a list of inventory items with their quantities and let the user update a quantity by typing into a text field, raise or lower an item by one using plus and minus buttons, and delete an item using a trash icon. It also had a login screen that checked whether an account already existed and offered to create one if it did not. The enhanced version is that same application rebuilt as a web application, with an Angular frontend, a PHP REST API built on the Restler framework, and a MySQL database accessed through Doctrine ORM. The original artifact was created in CS 360 and the enhancement work described here was done during CS 499.

I selected this artifact because its limitations were architectural rather than cosmetic. The application worked, but everything about it was tied to one device. The data lived in a SQLite file that no other user or device could reach, the interface code and the data access code were mixed together in the same Java classes, and there was no boundary where another client could ever be attached. Improving it in any meaningful way meant redesigning it instead of adding features to it, which is what makes it a good fit for the software design and engineering category.

The parts of the enhancement that best show my skills are the ones concerned with boundaries. The most important decision was making the REST API the contract between the frontend and the backend. The Angular client sends and receives JSON over HTTP and knows nothing about SQL, Doctrine, or the schema, which is what allows either half to be replaced without touching the other. I applied the same thinking to the data layer by defining a repository interface in the domain layer and implementing it separately with Doctrine in the infrastructure layer. The controllers depend on the interface rather than the ORM, and the single place that decides which implementation is used is the composition root. That decision had a practical payoff, because it let me write an in memory version of the repository for testing and unit test the whole authentication flow without a database or an HTTP request.

I also treated security as part of the design rather than something added afterward. Passwords are hashed with Argon2id instead of the PHP default, which is still bcrypt, because bcrypt only makes an attacker spend processing time while Argon2id also forces them to spend memory. The user entity has no getter for the password hash, so it cannot leak through serialization, and Doctrine still populates it through reflection. Authentication uses JSON Web Tokens signed with HS256, and the verifier states which algorithm it expects instead of trusting the algorithm named in the incoming token, which is what stops a forged token from being accepted. Login returns the same error for a wrong password and a username that does not exist, and spends the same hashing work on both, so neither the message nor the response time reveals whether an account exists. The API is also checked on every change by PSR-12 formatting rules, PHPStan static analysis at level 6, and a test suite that currently sits at 55 tests and 96 assertions.

In Module One I aligned this enhancement with three course outcomes, and I met two of them fully. I met the outcome about designing and evaluating computing solutions while managing trade-offs. Decoupling the frontend from the backend gives me independent deployment and the ability to add other clients later, and it costs a network hop and a more complicated local setup. Moving from SQLite to a networked database gives multiple users access to the same data and costs latency and operational expense. In each case I decided what I was giving up, not just what I was gaining. I also met the outcome about using well founded techniques and tools, since the stack reflects how these systems are built now, including a standalone component Angular application, a stateless token based API, an ORM with versioned migrations, and containers pinned to exact versions.

I partially met the outcome about professional quality communication. This narrative and the written reasoning kept with the code cover the written part, but the architecture diagrams and API documentation I planned are not finished yet, and I intend to complete them before the final ePortfolio submission. I do have one update to my outcome coverage plan. In Module One I assigned the security mindset outcome mostly to the databases category, but this enhancement has already covered a good deal of it. Deciding where authentication happens, what a token carries, and which layer is responsible for credentials turned out to be structural questions that had to be answered while designing the system. Protection against SQL injection worked the same way, since it comes from every value reaching the database as a bound parameter rather than from filtering input. I now expect this category to carry real weight for the security outcome as well.

I also want to be clear about what is finished. The architecture, the data layer, and the full authentication flow including account creation, login, token issuing, token verification, and a protected endpoint all work end to end from the Angular client through the API to the database. The inventory screens themselves, meaning the product list with the quantity field, the plus and minus buttons, and item removal, are not rebuilt yet and are the next piece of work. I also changed one decision from my Module One plan. I moved from AWS Aurora MySQL to AWS RDS MySQL, because Aurora’s distributed storage and higher availability are not worth the added cost at this application’s scale, and RDS gives me the same managed service benefits more simply. The cloud database is not provisioned yet, so everything currently runs against MySQL in a container using the same migration that will be applied to RDS.

The clearest lesson from this milestone was the difference between believing something works and checking that it does. I first chose the newest stable version of PHP for the API on the assumption that newer is better. Instead of trusting that, I ran the project on both candidate versions and found that the newer one produced a deprecation warning on every request, coming from a dependency of Restler that had no upgrade available. Pinning to the older version was the right call, but I would not have known to make it without testing first. I also created a bug while trying to clean something up. Doctrine’s schema validator kept reporting the migrations tracking table as unexpected, so I filtered that table out of the check. The filter worked, and it also hid the table from the migrations tool itself, which then reported that no migrations had run even though the record was sitting in the database. Running the migration again would have tried to recreate tables that already existed. I reverted the change and accepted a visible warning instead, because a loud harmless warning is safer than a silent dangerous one. It taught me that a change made only for tidiness deserves the same review as one that adds a feature.

The challenge that took the most time was not in my code at all. PHP-FPM clears the environment before starting its worker processes, and the PHP development configuration leaves the environment out of its variable order setting, so the values I passed into the container never reached the application. Either problem alone produces an app that reports a healthy database container while being unable to connect to it, with nothing useful in the logs.

The last thing I learned was that a security control can be defeated from a direction it was never meant to cover. I put real effort into making sure the login endpoint gives away nothing about whether an account exists. Later I realized the registration endpoint gives away the same thing, because it must tell a user that a username is taken. My first instinct was to make the registration error vague, and then I worked out that this does not help. Someone can register a name with a password they choose and then try to log in with it, and the result tells them whether the account already existed no matter what the error message said. That turned the problem from a wording choice into a design question about who should be allowed to create accounts at all, which is a decision I documented and deferred rather than covered up.
