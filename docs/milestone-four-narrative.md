# Milestone Four Narrative: Databases

Yaumel Betancourt

CS 499 Computer Science Capstone

Southern New Hampshire University

08/09/2026

The artifact is the inventory tracker application I originally built in CS 360 Mobile Architecture and Programming. It was an Android application written in Java that stored everything in a local SQLite database on the device. The software design category dealt with breaking the application apart into a web system, and the algorithms category dealt with how the data is searched and sorted. This category deals with the data itself, meaning where it lives, what rules protect it, and who is allowed to touch it. In the original version, the database was a single file on one phone; the schema existed only as a string of SQL inside the code. Every rule about valid data lived in the application, and passwords were stored using a hash with no salt. The enhanced version runs on MySQL 8.0.46 hosted on AWS RDS, defines its schema through versioned migrations, enforces its rules in the database rather than only in code, encrypts its connections, and gives the application account the narrowest set of permissions it can operate with.

I included this artifact because the database is the part of a system where mistakes are permanent. A bad function can be rewritten and redeployed in minutes. Corrupted data, a lost update, or a leaked credential cannot be undone by shipping a fix. That difference is what makes database work worth showing, and it is why most of the decisions in this category are about making bad states impossible rather than about making good states convenient.

The clearest example is where the rules live. In the original application, the rule that stock cannot be negative existed only as a check in Java, which means it held exactly as long as every code path remembered to call it. In the enhanced version the products table carries a check constraint that refuses a negative quantity no matter what sends the statement

The second component is the schema itself. Rather than a block of SQL that runs on first launch, the schema is defined by entity classes and applied through five versioned migrations that run in order and record what has already been applied. The same schema can be rebuilt from nothing on any environment, and a schema change is reviewable in a pull request like any other code.

The third component is concurrency, which I consider the strongest piece of work in the project. The original quantity update read the current value, adjusted it in code, and wrote the result back. To find out how badly that behaves, I sent one hundred simultaneous decrements at a product holding one hundred units. Forty-one of them vanished with no error reported to anyone. The fix does the arithmetic and enforces the floor inside a single conditional update statement, so the database decides the outcome rather than the application. Rerunning the same test loses nothing, and twenty simultaneous decrements against a stock of five produce exactly five successes and fifteen refusals.

The fourth component is access control. The application connects as an account holding only select, insert, and update on the one schema. It cannot create tables, drop them, delete rows, or grant itself anything. Migrations run as a separate and more privileged account at deploy time, so the credentials the running application holds are never the credentials that can reshape the database. I verified this rather than assuming it by connecting as the application account and attempting each forbidden operation, and the database refused every one of them.

The last component is protection of the data itself. Passwords use Argon2id, which generates a unique salt for every password, replacing the unsalted hashing in the original. Storage is encrypted, backups are retained, and the instance is not reachable from the public internet. Connections are encrypted with TLS, and rather than leaving that as an option the client chooses, the server requires it, so an unencrypted connection is refused before it can authenticate.

In Module One I aligned this category with three course outcomes, and I met all three.

I met the outcome about using well founded techniques and tools. Versioned migrations, composite indexes ordered with the equality column before the range column, check constraints, parameterized statements, unique constraints, soft deletion, and separate accounts for schema changes and application traffic are all standard database practice. I also used the tools as they are meant to be used, reading query plans to confirm index behavior instead of assuming it, and running an integration test suite against real MySQL rather than only against test doubles.

I met the security outcome. Argon2id with a per password salt, an application account restricted to three statement types, enforced TLS, a database level constraint that cannot be bypassed by application code, and parameterized queries that I tested with injection payloads all address the same idea, which is that the database should not depend on the application behaving correctly.

I met the outcome about designing and evaluating computing solutions while managing trade-offs. Soft deletion keeps history and holds the SKU reserved, at the cost of every query filtering on an active flag and of retired rows accumulating forever. Restricting the application account means a future feature that needs to delete rows will require a deliberate grant rather than working by default, which I think is the correct direction for that friction to run.

I do have one update to the plan, and it concerns the schema design. My Module One document contradicted itself. The summary listed a foreign key associating each inventory item with the user who owns it, while the detailed design in the same section described two independent tables with no relationship between them. I built the independent version and dropped the foreign key deliberately. The application has no concept of per user ownership. Every signed in user works with the same shared inventory.

The lesson I keep returning to is that a database is unforgiving of small assumptions, and that most of my mistakes in this category came from something I did not think was a decision at all. The first was version drift. My local database ran MySQL 8.0.40 and I planned to match it exactly in the cloud, but RDS no longer offers that version, and its oldest release is 8.0.42. I moved both environments to 8.0.46 rather than letting them differ, because the performance measurements from the previous category are only meaningful if the same optimizer produced them. While doing that I found another subtle drift, since MySQL 8 defaults to a different collation than my local container used, so I pinned the character set, collation, and time zone to match. Nothing would have failed loudly if I had missed it. Text comparison and sorting would simply have behaved differently in the two environments, which is the kind of difference that surfaces later as a bug nobody can reproduce.

The second lesson came from breaking the migration system while trying to tidy it. A schema validation command was emitting a harmless warning about the migrations tracking table, and I silenced it by filtering that table out of the schema comparison. The filter also hid the table from the migration tool itself, which then reported that zero migrations had been applied even though the records were sitting in the table. Running migrations again would have tried to recreate tables that already existed. What I took from it is that the mechanism protecting the schema is not the place to make cosmetic changes, and that a tool reporting a suspiciously clean result deserves more suspicion than a tool reporting an error.

The third lesson was that a soft delete is only half a feature. I had implemented retirement without a way back, which made it a one way door, and while testing I found that quantities could still be changed on a retired product and that those writes were reaching the database. I added a restore path and a guard that refuses stock movements on retired items, and I placed the check against the record already loaded in memory so a rejected change costs no write at all. The underlying mistake was that I had introduced a lifecycle with two states and only implemented one transition. Once data has a lifecycle, every transition in it must be designed, including the ones that undo the others.
