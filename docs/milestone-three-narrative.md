The artifact is the same inventory tracker application I originally built in CS 360 Mobile Architecture and Programming. It was an Android application written in Java that kept its data in a local SQLite database on the device. Where the software design category dealt with re-architecting the application into a web app, this category deals with how the inventory data itself is stored, searched, sorted, and filtered. In the original version the products were shown in a plain list with no way to search or reorder them, so finding one item meant scrolling through everything. The enhanced version adds prefix search across name and SKU, sorting by four different columns, a low stock filter with an adjustable threshold, and pagination, with the work pushed into indexed database queries rather than done in application memory. The original artifact was created in CS 360 and this enhancement was done during CS 499.

I selected this artifact because its data handling problems only appear at scale, which makes it a good place to show that I can reason about cost rather than just correctness. A list of ten products works fine no matter how you search it. A list of twenty thousand does not, and the difference between an approach that scales and one that does not is invisible until you measure it. To make that real I seeded the database with twenty thousand products and used MySQL explain and explain analyze to check what the database actually does with each query instead of trusting what I assumed it would do. The parts that best show these skills are the ones where a measurement changed the design. Search is the clearest example. My original plan searched name and SKU together in one condition, which reads naturally and is what most people would write. Measured against twenty thousand rows, it examined 14,834 rows to return 25, because the database cannot narrow its scan on one column when a row might qualify on the other. I restructured it as a union of two single column lookups so each half gets its own range scan. That brought it down to 2,403 rows examined, which is the number of rows that actually match, and cut the time from 6.89 milliseconds to 2.95.

Index design is the second piece. The low stock filter is served by a composite index on is_active and quantity in that order, because an index can only narrow left to right and stops narrowing once it hits a range condition. Putting the equality column first lets the database seek directly to the active rows and then scan a contiguous slice of quantities. Measured, that filter examines 357 rows out of 20,010 and returns in 0.41 milliseconds. The same principle drove a second composite index on is_active and name that serves both the default listing and the name half of the search.

The third piece is the hash map, and I want to be honest that it ended up somewhere different from where I planned it. My plan described using a hash structure for constant time lookups by product ID. The place it actually became necessary was inside the new search. The first query returns a sorted, paginated list of matching IDs, and the second loads those products, but the database returns them in whatever order it likes, so the sort has to be reapplied. Doing that by searching the result list for each ID would be linear per lookup and quadratic overall. Building a hash map keyed by ID makes each lookup constant time and the whole reorder linear. The data structure is there because the algorithm needed it rather than because the plan called for one.

Two smaller pieces round it out. Sortable columns are defined as a PHP enum rather than a list of allowed strings, so the set of valid sort columns is enforced by the type system and an unrecognized value cannot reach the query at all. Search patterns append the wildcard rather than prepending it, since a leading wildcard cannot use an index, and any percent or underscore a user types is escaped so it matches as a character instead of behaving as a wildcard.

In Module One I aligned this category with three course outcomes and I met all three.

I met the outcome about designing and evaluating computing solutions while managing trade-offs. Every significant decision here came with a cost I had to weigh. Pushing search into the database avoids transferring the whole table but ties the design to what the index can do. The union approach examines only matching rows but has to materialize all of them, while the original approach could stop early once it had a full page, so which one wins depends on how selective the search is. Adding indexes speeds up reads and slows down every insert and update, which is why I later removed one that had become redundant.

I met the outcome about using well founded techniques and tools. Prefix matching that an index can use, composite indexes ordered equality before range, keyset friendly sorting with a matching tiebreak, pagination that limits both rows and memory, and an atomic conditional update for concurrent changes are all established practice rather than invention. I also used the tools properly by reading query plans instead of guessing. I met the security outcome, which in Module One I tied specifically to validating the sort column against an allow-list. That was implemented, and I went further than planned. The sort column cannot be parameterized because it is an identifier rather than a value, so the enum is the only thing standing between user input and the query. Beyond that, every value reaches the database as a bound parameter, and I tested the endpoints with injection payloads to confirm it. I also added a database level check constraint so stock cannot go negative regardless of what the application does. The one update to my plan is the claim about complexity. In Module One I wrote that an indexed search would run in roughly logarithmic time against a linear scan. The measurements do not support stating it that simply. What I can support is that the search now examines a number of rows proportional to the number of matches instead of proportional to the size of the table, and I have the row counts and timings to show it. I would rather make the smaller claim that the evidence supports.

The strongest lesson was that measuring changed my mind more than once, and usually about something I was confident in. My first fix for the search made it slower. I replaced the combined condition with a union expecting an immediate win, and it went from 6.89 milliseconds to 10.8. The union was correct in principle but the name half of it still could not use an index efficiently, because the index on name did not include the active flag and the database had to choose between filtering on one and scanning the other. It chose wrong and examined 19,613 rows. The fix was a second change, a composite index with the equality column first, and only with both changes together did the approach pay off. Two correct ideas were not enough on their own, and if I had stopped after the first I would have shipped something worse while believing I had improved it.

The second lesson came from a bug that a full test suite failed to catch. My search used a bound parameter for the escape character, which the query language does not allow in that position. Every search request would have failed. Fifty five unit tests passed anyway, because they ran against an in memory test double that accepted a query the real database would reject. I built an integration test layer that runs against real MySQL, and then confirmed it was worth having by deliberately reintroducing the bug. The unit tests passed 118 out of 118 while the integration tests failed immediately. Tests against a double verify your logic, and only tests against the real database verify your queries.

The third lesson was about concurrency, and it was the most counterintuitive. My quantity adjustment read the current value, added the change in code, and wrote the result back. To see how bad that was I fired one hundred simultaneous decrements at a product with a stock of one hundred. Forty one of them disappeared with no error reported to anyone. What surprised me was that the naive version could never produce a negative number, because each request writes an absolute value it computed, so the worst case is that updates are lost rather than that stock goes below zero. Making the update atomic fixes the lost updates and reintroduces the risk of a negative, so both properties have to be handled in the same statement. The version I settled on does the arithmetic and enforces the floor in one update, backed by a database constraint. Rerunning the same test now loses nothing, and twenty simultaneous decrements against a stock of five produce exactly five successes and fifteen refusals.

The last thing I learned is that removing an index can be as considered a decision as adding one. Once the composite index existed, the older single column index on name was only useful for one uncommon query, and it cost write performance on every insert and update. I expected dropping it to make that query fall back to a full scan. Instead the database used a skip scan on the composite index and the timing barely moved, because the active flag has only two possible values. The low cardinality that made that column useless as an index on its own was exactly what made the skip scan work.
